# Security

The Network holds private notes about everyone its owner knows. It is a single-user app on the
open web, so the design assumes the URL is public and the password may one day leak.

## Reporting a vulnerability

Please don't open a public issue. E-mail the maintainer (see the Git history for the address)
with steps to reproduce; you'll get an answer within a few days.

## Sign-in

Two factors, both required by default:

1. **Password** — Supabase Auth (email + password). Sign-up is disabled on the Supabase project;
   the app has no sign-up screen. Passwords: at least 12 characters with letters and digits
   (`src/lib/security/password.ts`), ideally generated by iCloud Keychain.
2. **Passkey** — Face ID / Touch ID via WebAuthn (SimpleWebAuthn, `src/lib/auth/webauthn.ts`).
   Supabase's own WebAuthn MFA isn't available on the hosted project, so the second factor is
   implemented in the app:
   - After a passkey assertion the server sets `__Host-network-mfa`, an HMAC-signed, httpOnly,
     Secure cookie bound to the Supabase `session_id` (30 days). A new sign-in means a new session
     id, which invalidates the cookie.
   - The proxy (`src/proxy.ts`) and every API handler (`withOwner`) require it. Route classes live
     in `src/lib/auth/routes.ts`; anything new is protected by default.
   - WebAuthn challenges travel in a signed 5-minute cookie bound to user, session and ceremony.
   - **Enrollment:** with no passkey enrolled, a password session may enroll the first one
     (bootstrap). After that, adding/removing passkeys, regenerating recovery codes and changing
     the password require a passkey-verified session. Removing the last passkey is refused while
     passkeys are required.
   - **Recovery codes:** 10 one-time codes, shown once at first enrollment (or on regeneration),
     stored only as HMAC hashes keyed from `APP_SECRET`. Redeeming one is rate-limited and sends
     an e-mail.
   - **Alerts:** adding a passkey or using a recovery code e-mails the owner (when Resend is set
     up).
   - `AUTH_REQUIRE_PASSKEY=false` (local development / self-hosters who opt out) makes the
     passkey optional; the app then offers it gently (`PasskeyPrompt`).

Password reset: "Forgot password?" e-mails a Supabase PKCE link → `/auth/callback` →
`/login/reset`. The reset page needs the recovery session but not the passkey, so a leaked
mailbox can change the password but still can't open the data. Other sessions are signed out
after a reset or a password change.

Sessions on trusted devices are long: Supabase refresh tokens + the 30-day passkey cookie.
**Sign out** (`signOutEverywhere()` in `src/lib/auth/signout.ts`) clears the passkey cookie,
revokes this device's Supabase session, wipes the in-memory and IndexedDB query caches and all
runtime caches (only the public app-shell precache stays). A session that merely lapses keeps
the caches, so offline edits survive until the owner signs back in. "Sign out other devices"
(Settings → Security) revokes every other session.

## Secrets

| Variable | Purpose |
| --- | --- |
| `APP_SECRET` | Root key (≥ 32 chars). Per-purpose keys are derived with HKDF (`src/lib/crypto/keys.ts`): passkey cookie, WebAuthn challenges, recovery-code hashes, e-mail link signatures. Rotate by moving the old value to `APP_SECRET_PREVIOUS`. |
| `CRON_SECRET` | Bearer token for `/api/cron/reminders` (Vercel Cron, Supabase `pg_cron`). Header only — never in a query string. |
| `INBOX_TOKEN` | Bearer token for the iPhone Shortcut endpoint `/api/inbox`. Never returned by any API. |

Bearer secrets are compared in constant time (`src/lib/security/compare.ts`).

## E-mail action links

Digest buttons ("Done", "Snooze a week") are signed, expiring links (HMAC with the
`link-signing` key, 30 days). They open a confirm page (`/r/<id>/<action>`) — opening it changes
nothing, so link-scanning mail filters are harmless — and the tap POSTs the signature back to
`/api/reminders/<id>/<action>`, which verifies it again. Actions are idempotent. Links sent
before this scheme (signed with `CRON_SECRET`) keep working until they expire, and never past
31 Jan 2027; delete the legacy branch in `src/lib/signing.ts` after that. `/r/*` is served with
`Referrer-Policy: no-referrer` so the signature can't leak.

## HTTP headers

Set in `next.config.ts` (`src/lib/security/headers.ts`) for every response:

- `Strict-Transport-Security: max-age=63072000; includeSubDomains` (production only)
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin`
- `Referrer-Policy: strict-origin-when-cross-origin` (`no-referrer` on `/r/*`)
- `Permissions-Policy: camera=(), microphone=(), geolocation=(), publickey-credentials-get=(self), publickey-credentials-create=(self)`
- `X-Robots-Tag: noindex, nofollow`, plus `robots.txt` disallowing everything and `noindex` metadata
- no `X-Powered-By`

## Content Security Policy — static vs. nonce

Builders and tests: `src/lib/security/csp.ts`. Two policies, on purpose:

**Static policy (app pages + API).** App pages are statically rendered so they prefetch
instantly and open offline from the service worker. A static page can't carry a per-request
nonce, and Next.js streams its RSC payload in inline `<script>` tags, so `script-src` needs
`'unsafe-inline'`. Everything else is locked down: `default-src 'self'`, `object-src 'none'`,
`base-uri 'self'`, `frame-ancestors 'none'`, `form-action 'self'`, and `connect-src` limited to
the app, Supabase and the map tile host. Script files carry Subresource Integrity hashes
(`experimental.sri`), so a tampered CDN file won't run. The residual risk — an injected inline
script — rests on React's output escaping; never render untrusted HTML without sanitising it.

**Nonce policy (the sign-in surface).** `/login`, `/login/verify`, `/login/reset` and
`/oauth/consent` render per request anyway (`await connection()`), so the proxy issues a fresh
nonce: `script-src 'self' 'nonce-…' 'strict-dynamic'` — no `'unsafe-inline'` where the password
and passkey are entered. Next.js applies the nonce to its own scripts; the root layout's single
inline script (pre-paint theme) is allowed by its SHA-256 hash instead of reading the nonce,
because reading request headers in the shared layout would make every page dynamic.

`style-src` keeps `'unsafe-inline'` in both: inline style attributes (Motion, Base UI
positioning) can't be nonced, and style injection is a far smaller risk than script injection.

**Rollout.** Both policies ship as `Content-Security-Policy-Report-Only`, reporting to
`/api/csp-report` (rate-limited, size-capped, logs scrubbed of query strings; search the logs for
`csp-violation`). Once reports are quiet in production, set `CSP_REPORT_ONLY = false` in
`src/lib/security/csp.ts` to enforce.

## Service worker

`src/app/sw.ts` never caches private data in Cache Storage: same-origin `/api/*`, `/auth/*`,
`/oauth/*`, `/r/*`, `/login*` and Supabase requests are network-only (the offline copy of data is
the TanStack Query cache, which sign-out wipes). Map tiles, glyphs and sprites from
`tiles.openfreemap.org` are cached for 30 days.

## CSRF

Session cookies are `SameSite=Lax`, API writes take JSON bodies, and the sign-in endpoints under
`/api/auth/*` additionally require a same-origin `Origin` header.

## Release checklist

1. Set `APP_SECRET` (`openssl rand -base64 48`), `CRON_SECRET`, `INBOX_TOKEN`; leave
   `AUTH_REQUIRE_PASSKEY` unset (required).
2. Deploy, then **immediately** sign in and enroll Face ID — until the first passkey exists, the
   password alone can enroll one.
3. Save the recovery codes (password manager note or paper), then add a second passkey from
   your other device (Settings → Security).
4. In Supabase: keep sign-ups disabled, set the site URL / redirect URLs to the production
   `/auth/callback`, enable leaked-password protection.
5. Watch `csp-violation` logs for a while, then enforce the CSP.
